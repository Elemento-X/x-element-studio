## Pegadinhas encontradas

### 1. Cache `.next/` segura referências fantasmas

Após mover `layout.tsx`/`page.tsx`, `tsc --noEmit` reclamou de `Cannot find module '../../../app/page.js'` em arquivos do `.next/types/`. Cache do dev server prévio.

**Mitigação:** `rm -rf .next` antes do primeiro typecheck/build na branch i18n. Em F4: garantir que CI faz checkout limpo (já faz) e que devs locais conhecem essa pegadinha.

### 2. Imports relativos das fontes WOFF2 quebraram

`localFont({ src: [{ path: '../public/fonts/...' }] })` precisa virar `'../../public/fonts/...'` no layout movido (1 nível mais profundo).

**Mitigação:** já corrigido no spike. Em F4, validar que **toda** referência relativa em `app/layout.tsx` é re-baseada (fontes, `globals.css`, qualquer asset).

### 3. Imports de `_components/` ficaram quebrados com paths relativos

`./_components/Hero/Hero` no `app/page.tsx` antigo virou import relativo errado no `app/[locale]/page.tsx`.

**Mitigação:** trocar todos para alias absoluto `@/app/_components/...`. Já feito no spike. Em F4, **regra:** todos os componentes da landing usam alias absoluto (não relativo) — evita re-baseamento futuro se a estrutura mudar de novo.

### 4. Composição middleware: ordem importa

next-intl middleware faz redirect/rewrite. Se você setar headers e DEPOIS chamar `intlMiddleware`, perde-os. Ordem correta:

```ts
const response = intlMiddleware(request) as NextResponse  // 1º
response.headers.set('Content-Security-Policy', CSP)       // depois
```

A inversão (chamar `intlMiddleware` depois de criar um `NextResponse.next()`) **não funciona** — o response do intl substitui o seu.

### 5. `setRequestLocale` dentro do layout precisa de `await params` antes

```ts
const { locale } = await params           // params é Promise no Next 15+
if (!hasLocale(routing.locales, locale)) notFound()
setRequestLocale(locale)                  // só aqui — não antes do await
```

Sem isso, `setRequestLocale` recebe `undefined` e a static rendering quebra silenciosamente em runtime (page vira dynamic mesmo com `generateStaticParams`).

### 6. `generateStaticParams` retorna `[{ locale }]`, não `[locale]`

Pequeno detalhe da API. Esquecer = build OK mas rotas viram dinâmicas.

### 7. Plugin `createNextIntlPlugin` é obrigatório no `next.config.mjs`

Sem o plugin, as mensagens não carregam em RSC (erro só dispara em runtime, não em build). Usar `withNextIntl(nextConfig)` envolvendo o export.

### 8. Não testado neste spike (mas mapeado)

- **Hydration mismatch**: client components que renderizam strings diferentes server vs client (ex: data formatada). Não há nenhum no F2/F3 atual, mas se aparecer com `useTranslations` em client component, vai precisar de `NextIntlClientProvider` carregando `messages` no provider. O spike já adicionou `NextIntlClientProvider` no layout sem messages explícitas — funciona porque os components atuais não consomem traduções ainda.
- **`hreflang` SEO**: não validado. Em F4 incluir `alternates.languages` no metadata + sitemap por locale.
- **E2E existentes** apontam para `/`. Vão precisar atualizar pra `/pt-br` (default) ou seguir o redirect.

## Recomendação para F4

**PROSSEGUIR.**

O shape funciona end-to-end:
- Build verde
- Smoke verde nos 3 locales
- CSP + headers estáticos preservados
- next-intl middleware compõe limpo com nosso middleware existente
- SSG mantido via `generateStaticParams`
- Cache `.next/` é a única pegadinha real, e é trivial mitigar

R-8 (App migration breaks build) **fica fechado** com este spike. A migração é mecânica, sem decisões arquiteturais bloqueantes.
